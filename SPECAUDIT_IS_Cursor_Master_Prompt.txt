You are a senior full-stack engineer, AI/NLP engineer, product designer, and system architect.

I am rebuilding a project called:

SPECAUDIT-IS
AI Tender Auditor for Indian Standards

This project is being developed for Smart India Hackathon 2026, Problem Statement SIH26108:

"AI-Powered Indian Standards Recommendation Engine"

The goal is to build a production-quality prototype that helps procurement officers analyze tender specifications, identify applicable Indian Standards, verify versions/amendments/certification requirements, detect missing or vague requirements, perform decision-point/coverage analysis, and produce an auditable improved tender draft.

IMPORTANT:
This is NOT supposed to be a generic chatbot.
It is an AI-assisted procurement auditing and Indian Standards recommendation platform.

The system must be:
- explainable
- traceable
- evidence-oriented
- human-in-the-loop
- auditable
- modular
- scalable
- visually polished
- suitable for an SIH demonstration

Do not create fake claims about real BIS data.
When real registry data is unavailable, use clearly labelled DEMO/SAMPLE data.
Never present synthetic/demo standards as verified real BIS information.
Every recommendation should have a source/evidence state.
The officer must remain the final decision-maker.

==================================================
2. CORE PROBLEM
==================================================

Procurement tenders often contain:
- vague requirements
- missing technical parameters
- outdated Indian Standard references
- incorrect or incomplete standard references
- missing testing requirements
- missing certification requirements
- missing marking requirements
- missing grades/classes
- missing safety requirements
- missing allied/normative standards
- ambiguous wording
- open buyer decisions

Thousands of standards may overlap, reference each other, be amended, replaced, or withdrawn.

The system must help officers determine:
1. What requirements are actually present in the tender?
2. Which Indian Standards apply?
3. Which allied/normative/testing/safety standards are relevant?
4. Which version was valid on the tender date?
5. Which amendments matter?
6. Which BIS/QCO/CRS/certification requirements apply?
7. Which decision points are missing?
8. Which clauses are vague or non-measurable?
9. Which requirements are only partially covered?
10. What should be changed in the tender?
11. Why did the system make each recommendation?
12. What did the officer approve/reject/modify?

==================================================
45. DATA SAFETY / TRUST
==================================================

Rules:

1. Never hallucinate an Indian Standard.
2. Never invent standard numbers.
3. Never invent clauses.
4. Never claim a standard is active unless registry data says so.
5. Never claim certification is mandatory without supporting data.
6. Clearly mark unknown/unverified data.
7. Store registry snapshot date.
8. Preserve audit reproducibility.
9. Keep officer approval explicit.
10. Never silently modify approved content.

Use states:

VERIFIED
UNVERIFIED
UNKNOWN
DEMO
OUTDATED
WITHDRAWN
REQUIRES_REVIEW


==================================================
46. COPYRIGHT
==================================================

Do not store or reproduce full copyrighted BIS standards text.

Store:
- metadata
- standard number
- title
- year
- status
- amendment facts
- clause identifiers
- evidence pointers
- official source URLs
- registry facts

When displaying source information:
show concise factual references and links to official sources.

Respect copyright.

60. FINAL DESIGN PHILOSOPHY
==================================================

The most important interaction is:

Requirement
→ Why?
→ Which Standard?
→ Why this Standard?
→ Is the Version valid?
→ Is Certification required?
→ What evidence supports it?
→ What decision point is covered?
→ What is missing?
→ What should change?
→ Did the officer approve it?

Build the product around this interaction.

The user should never see an unexplained AI recommendation.

Every important recommendation should have:

Recommendation
Confidence
Evidence
Source
Verification status
Officer action

Build the application incrementally, keep the architecture clean, use reusable components, and make sure the application runs after each phase.

Start by creating the complete project structure, database schema, design system, routing, and demo data.

Then implement the dashboard and core audit workflow.

Do not attempt to implement all AI functionality with hardcoded fake logic. Create clean service interfaces and use deterministic demo implementations where external AI/registry infrastructure is not available.

When a real AI/registry integration is unavailable, clearly label the implementation as DEMO and keep the architecture ready for the real service.

The final result must be coherent, polished, technically credible, and aligned with SIH26108.
